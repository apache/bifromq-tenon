# cargo-tenon

Tenon is part of Apache BifroMQ (Incubating). See the [incubation disclaimer](../../../DISCLAIMER).

Build, validate and package Rust plugins for Tenon. `cargo-tenon` compiles your program, checks its configuration and payload definitions, and creates an installation archive.

## Installation

You need Rust 1.99.0, Cargo, and a native compiler/linker. The Rust packages use edition 2024. Install the tool from a Tenon source checkout:

```bash
cargo install --path sdk/rust/cargo-tenon --locked
cargo tenon --help
```

Ensure Cargo's installation bin directory (normally `$HOME/.cargo/bin`) is on `PATH`. You can also invoke `cargo-tenon` directly with the same arguments.

The required `[package.metadata.tenon]` fields `display-name` and `description` become the manifest's `displayName` and `description`. Use 1-80 Unicode code points for a single-line name and 1-1024 for a description; both require non-whitespace plain text. Descriptions may contain LF/CR line breaks. Values are preserved, not inferred from Cargo package metadata or the Program identifier. See the [display metadata contract](../../../guide/plugins.md#display-metadata).

## Commands

Run these in the plugin package directory:

```bash
cargo tenon build
cargo tenon bundle --release
cargo tenon check /absolute/path/to/unpacked-package
```

| Command | Input and result |
| --- | --- |
| `build` | Compiles one Cargo package, validates its contracts, and reports the executable and descriptor paths. It does not produce an archive. |
| `bundle` | Performs the same build and validation, then writes a `.tar.gz` installation bundle. |
| `check` | Reads `manifest.json`, `config.schema.json`, and `payload.descriptor.pb` from an existing directory. It neither compiles nor executes the plugin and does not change the input files. |

`check` takes an unpacked contract directory, not a Cargo project or a `.tar.gz` file. It does not check whether the manifest's command can run.

`build` and `bundle` accept:

| Option | Meaning |
| --- | --- |
| `--manifest-path <Cargo.toml>` | Select a concrete package. The default is `Cargo.toml` in the current directory. A virtual workspace is not a package. |
| `--release` | Use Cargo's release profile instead of debug. |
| `--target <triple>` | Compile for this target. Without it, use the host reported by `rustc -vV`; target settings in Cargo configuration do not select the target for this tool. |
| `--locked`, `--offline`, `--frozen` | Forward the corresponding dependency-resolution constraint to Cargo. |
| `--config <KEY=VALUE>` | Forward a Cargo configuration override. May be repeated. |

For example, build for Apple Silicon:

```bash
cargo tenon bundle --release --target aarch64-apple-darwin
```

Accepted targets are `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, and `aarch64-unknown-linux-musl`. Install the target's Rust standard library and provide the required cross compiler, linker, and libraries when cross-compiling. The tool does not install them.

## Required project files

The package must have exactly one binary target. It supplies these inputs:

| Input | Purpose |
| --- | --- |
| `package.metadata.tenon.program-name` | The plugin's reverse-domain identity, for example `com.example.file-source`. |
| `package.metadata.tenon.interface` | Exactly `source`, `sink`, or `source-and-sink`. |
| `package.version` | The installed version. Do not maintain another version field. Tenon rejects SemVer build metadata such as `0.1.0+local`. |
| `config.schema.json` | The schema for the complete instance configuration, in the package directory beside `Cargo.toml`. |
| `OUT_DIR/payload.descriptor.pb` | The payload descriptor generated by this package's `build.rs`. |

For example, a Source package has:

```toml
[package]
name = "file-source"
version = "0.1.0"
edition = "2024"
rust-version = "1.99.0"

[package.metadata.tenon]
display-name = "File Source"
description = "Read records from a local file."
program-name = "com.example.file-source"
interface = "source"

[dependencies]
tenon-plugin-sdk = "=0.1.0"
```

The configuration schema must be strict JSON with an object root and `$schema` equal to `https://json-schema.org/draft/2020-12/schema`. References must stay inside the same document. Tenon does not fill in defaults or coerce user values; the `default` keyword is not accepted. A plugin with no settings can use:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "properties": {}
}
```

The descriptor must be a self-contained proto3 `FileDescriptorSet`, including imported files and source information. It must contain exactly one top-level `SourceRecordPayload` for a Source interface and exactly one top-level `SinkRecordPayload` for a Sink interface. A combined plugin includes both; a single-interface plugin must not include the other root. Protobuf Editions, proto2, custom options, unsupported types, and conflicting field names are rejected.

For a Source project using the SDK, a minimal `proto/source_record_payload.proto` is:

```proto
syntax = "proto3";
package plugin;

message SourceRecordPayload {
  string message = 1;
}
```

Add these build dependencies to `Cargo.toml`:

```toml
[build-dependencies]
prost-build = "=0.14.4"
protoc-bin-vendored = "=3.2.0"
```

Then use this `build.rs` to generate both the Rust types and descriptor from the same input:

```rust
use std::{env, error::Error, path::PathBuf};

fn main() -> Result<(), Box<dyn Error>> {
    println!("cargo:rerun-if-changed=proto/source_record_payload.proto");
    let output = PathBuf::from(env::var_os("OUT_DIR").expect("Cargo sets OUT_DIR"));
    let mut config = prost_build::Config::new();
    config.protoc_executable(protoc_bin_vendored::protoc_bin_path()?);
    config.prost_path("::tenon_plugin_sdk::prost");
    config.file_descriptor_set_path(output.join("payload.descriptor.pb"));
    config.compile_protos(&["proto/source_record_payload.proto"], &["proto"])?;
    Ok(())
}
```

This setup supplies `protoc` as a build dependency; the deployed plugin does not load `.proto` files or need `protoc`. For Sink or combined projects, change the input list to include the corresponding payload files. Your binary must implement the declared interface; contract validation does not execute that implementation.

`manifest.json` is generated for the selected OS/CPU with `command: ["./program"]`. Keep the generated descriptor in `OUT_DIR`; no project-root copy is needed.

## Bundle layout and deployment

Each bundle contains four regular files at its root:

```text
config.schema.json
manifest.json
payload.descriptor.pb
program
```

The three contract inputs must be regular files, not symbolic links. No extra resources, launch scripts, or dynamic libraries are collected. The manifest describes one OS/CPU combination; ABI differences such as GNU libc versus musl remain deployment requirements that the author must explain.

The archive is written beneath Cargo's reported target directory:

```text
tenon/<target>/<debug-or-release>/<package-name>-<version>.tar.gz
```

Identical executable and contract files produce identical archive bytes. A failed build, validation or archive write leaves an existing bundle intact.

Install the resulting archive through Tenon's plugin installation interface, configure an instance, and run a real data flow on the intended target. A successful build does not prove that runtime libraries, credentials, external services, or business behavior are correct. `cargo package` produces a registry source archive, not this installation bundle.

## Machine-readable results

Successful `check`, `build`, and `bundle` commands exit with code `0` and write one JSON line to stdout. `check` returns the package summary directly:

```json
{"programName":"com.example.file-source","exactVersion":"0.1.0","displayName":"File Source","description":"Read records from a local file.","interface":"source","platforms":[{"os":"darwin","architecture":"arm64"}],"sourceRoot":"plugin.SourceRecordPayload","sinkRoot":null}
```

`sourceRoot` and `sinkRoot` are fully qualified message names; a root for an undeclared interface is `null`. `build` wraps that summary in `package` and adds `target`, `executable`, and `descriptor`. `bundle` also adds `bundle`, the archive path. Paths come from the actual Cargo build and may differ between machines.

Failures exit with code `1` and write one JSON line to stderr:

```json
{"error":{"code":"payload_contract.source_root_missing","message":"missing top-level SourceRecordPayload"}}
```

Inspect `error.code` to identify the failed check and `error.message` for its explanation. Cargo compilation or linking failures are reported through the same error envelope.
